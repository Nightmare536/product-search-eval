# 选品检索评测引擎

> **一句话**：改完检索逻辑，你怎么证明它真的变好了？
>
> 口语化提问（"桌子上的线总是绞成一团"）在关键词检索下召回很差。
> 这个项目把检索拆成可插拔的策略，用一套固定的评测集，量化每一步改动的真实效果。

无第三方依赖，Python 3.8+。

---

## 结果

110 条商品 / 149 条人工标注提问 / TopK=10，指标为 Recall@10：

| 策略 | 全部 149 条 | 难例·纯意图（34 条） | 难例·新说法（20 条，未参与调参） |
|---|---|---|---|
| 1 纯关键词（第一版） | 0.886 | 0.500 | 0.275 |
| 2 BM25 + 同义词词典 | 0.899 | 0.559 | 0.325 |
| 3 混合召回 + RRF | 0.896 | 0.544 | 0.325 |
| 4 语义向量（LSA） | 0.851 | 0.566 | **0.500** |
| 5 意图改写 + BM25 | **1.000** | **1.000** | 0.475 |
| 6 意图改写 + BM25 + 向量 + RRF | 0.997 | 1.000 | **0.575** |

---

## 三个结论（这才是我想让人看的部分）

### 1. 向量召回解决的是"说法不一样"，不是"不知道想买什么"

LSA 语义召回把「新说法」从 0.325 提到 **0.500**（+54%），
但在「纯意图难例」上几乎没有变化：**0.559 → 0.566**。

这两组数字一起看才有意义：用户说"桌子上的线绞成一团"时，
缺的不是同义词，是**他没说出品类**（理线器）。向量再强也匹配不到一个不在查询里的词。

→ 瓶颈在**意图理解层**，不在召回层。

### 2. 词表能把难例刷到 1.000，但那是「照着题写答案」的上限

策略 5 在 34 条难例上做到 1.000——因为意图词表就是照着这批难例写的。
换成 20 条**写词表时没参考过**的新说法，直接掉到 **0.475**。

所以报告里永远两个数字一起报：一个给"能到多少"，一个给"换个说法还剩多少"。

### 3. 判断下一个动作，用的是数据不是直觉

泛化集只到 0.575，说明继续堆词表的边际收益已经很低（维护成本却线性上升）。
**结论：该上大模型做在线意图改写了**，而不是再写 200 个同义词。

这个判断不是拍脑袋——是 6 组策略 × 2 套评测集跑出来的。

## 失败案例（最诚实的一节）

最后一版策略在 20 条新说法上仍然没命中的 8 条，逐条列出：

| 用户的原话 | 期望商品 | 实际返回 Top3 |
|---|---|---|
| 经常在外面手机电量撑不到晚上 | 充电宝 | 手机壳、数据线、支架 |
| 酒店房间里能插电的孔太少了 | 插排 | 充电头、转换头、延长线 |
| **桌子上的线总是绞成一团** | **理线器** | **充电线、数据线、收纳袋** |
| 晚上用电脑，键盘那一片黑乎乎看不清 | 屏幕挂灯 | 台灯、键盘膜、鼠标垫 |
| 天冷了，想带热水出门 | 保温杯 | 水杯、杯套、茶具 |
| 耳机孔听歌不好听，想提升一下 | 解码耳放 | 耳机、耳机线、转接头 |
| 自己录视频想固定住，画面别晃 | 手机支架 | 三脚架、稳定器、夹子 |

每一条都不是"检索没找对"，是**检索根本不知道要找什么**。
这 8 条就是引入大模型意图改写的量化依据。

```python
class MyApiRetriever(Retriever):
    name = "线上版本"
    def search(self, query, topk=10):
        r = requests.get("http://your-server/api/search",
                         params={"q": query, "size": topk}, timeout=5)
        return [str(x["productId"]) for x in r.json()["data"]["list"]]
```

## 已知局限（不藏）

1. **商品数据只有 110 条，且词表来自商品库** → 0.997 这组数字偏乐观，换成真实商品库会下降。
2. **LSA 是无监督的降维，不是真 embedding** → 只到 0.500。换 bge-m3 / 百炼 embedding 才有可比性。
3. **策略 3 的"语义召回"是字符 n-gram 占位**，不是真向量检索；它相对策略 2 的提升主要来自 RRF 融合。
4. **意图词表是规则**，泛化能力就是它的天花板（0.475）。

第 1 条和第 3 条是面试时最容易被追问的地方，写在这里比被问出来好。

## 配套的 Java 实现

同一套策略在 SpringBoot 里重写了一遍（`../选品检索服务-java`），
迁移后指标与 Python 完全一致（0.997 / 1.000 / 0.575）——**先定验收标准，再重写**。

服务端额外的工程处理：

- 模型依赖用「有界队列线程池 + `Future.get(timeout)` + 丢弃迟到结果」兜住
- 模型需 2 秒时，接口 0.8 秒返回；40 并发 P99 834ms、零失败
- 结果缓存命中 0.37ms
